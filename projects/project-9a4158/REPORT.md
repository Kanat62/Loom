# 1. Задача

Сделать веб-сервис, который берёт горизонтальный видеоролик и превращает его в вертикальное видео (9:16) под экран телефона. Пользователь либо сам водит рамку мышью по кадру во время просмотра, либо включает автоматику — рамка сама едет к говорящему. Ручное и автоматическое ведение совмещаются: там, где пользователь провёл мышью, остаётся его правка, остальное ведёт автоматика. Результат — mp4 со звуком исходника, скачиваемый одной кнопкой, покадрово совпадающий с тем, что показывало превью.

# 2. Решения

Выбран вариант A: браузерный canvas-редактор для превью + Node/Express + один проход ffmpeg с crop, управляемым файлом sendcmd-команд.

Почему: признаки готовности 2 и 4 (мгновенная реакция рамки на мышь, точное переигрывание после перемотки) достижимы только при расчёте превью на клиенте, поверх `<video>`. Признак 8 (покадровое совпадение экспорта с превью, звук и длительность на месте) достигается, если финальный crop строится из той же дорожки выборок (30 Гц), что рисовала превью — один проход ffmpeg, звук копируется без перекодирования. Автоматика (признаки 5, 7) считается в браузере (лица + огибающая звука), а не на сервере, чтобы пользователь видел её работу сразу при просмотре, а не после серверного round-trip.

Отклонённые варианты: B (полностью клиентский рендер через WebCodecs) — противоречит §6 ТЗ и хрупок из-за ручного мукса mp4; C (покадровый PNG-конвейер) — на порядок медленнее для роликов «до нескольких минут»; D (серверный ML-анализ говорящего) — второй рантайм и заметная задержка перед тем, как пользователь увидит автоматику.

Единое инженерное решение из §6 — одна дорожка положений рамки (авто-слой + ручные перезаписи + клэмп по границам кадра) — реализовано как отдельный модуль ядра и стало основой сразу для нескольких признаков готовности (3, 4, 6).

# 4. Как проверено

Контур 1: каждая задача привязана к конкретным признакам готовности и формально закрыта. Явных агрегированных чисел «X критериев пройдено из Y» в моём распоряжении нет — есть только статусы задач и их covers-карта, которая целиком покрывает все 9 признаков.

Контур 2: Пилот прогнал продукт как пользователь, нашёл 1 замечание (findingsCount=1) — отсутствовала логика сброса состояния при загрузке нового файла поверх уже отработанной сессии. Замечание не визуальное (visual=false), скрипт проверки не падал (scriptFailed=false). Замечание закрыто отдельной задачей pilot_fix, признак 9 подтверждён повторно.

# 5. Что хромает

Формально всё done, но история задач показывает, что путь к этому статусу не был гладким, и часть рисков стоит знать:

- **Фикстуры**: приёмочный критерий изначально был математически недостижим — скрипт печатает лог в тот же stdout, с которым сравнивается строгое `equals 'FIXTURES_OK'`. Диагностика уровня «code» была исчерпана, требовалось архитектурное решение (перенос лога в stderr либо ослабление критерия до `contains`). Задача закрыта, но нужно убедиться, какой из вариантов реально применён — иначе критерий может при следующем прогоне снова не сойтись.
- **Ручное ведение мышью** и **Автоматика в браузере**: несколько попыток верификации упирались не в код, а в недоступность шлюза моделей (таймауты `claude-cli:opus`) — сценарии Playwright не доходили до проверки упора рамки в края, `sampleTrack`, `previewSrcRect`. То есть в какой-то момент у этих задач не было ни одного факта о реальном поведении, только план правок (code_hint). Финальный done означает, что позже проверка прошла, но у меня нет отдельного подтверждения, что именно кодовые правки, а не окружение, были причиной первых провалов — стоит перепрогнать эти сценарии ещё раз в спокойных условиях для уверенности.
- **Точность экспорта**: в одной из итераций сборка вообще не компилировалась (`renderRoutes.ts` не экспортировал то, что импортировал `index.ts`), и числовая проверка `mean_abs_pixel_diff` (FIDELITY_OK) ни разу не выполнялась. Задача сейчас done, но явного числового значения расхождения кадров экспорта с превью в отчётах, которые до меня дошли, нет — есть только факт, что критерий в итоге пройден.

В сумме: продукт закрывает все признаки готовности, но для трёх задач путь к done шёл через полностью проваленные прогоны (инфраструктурные и архитектурные), и у меня нет «чистого» финального протокола с цифрами по каждому критерию — только статус done.

# 6. Что требует тебя

Задач в статусе `blocked_needs_human` в дереве сейчас нет — все финализированы как done. Но в диагностике трёх задач прямо зафиксированы вопросы, адресованные человеку, и неясно, было ли по ним принято явное решение или проблема просто исчезла при повторном прогоне:

1. **Фикстуры** — нужно подтвердить, какой вариант принят: лог скрипта переносится в stderr, или критерий приёмки ослаблен до `contains 'FIXTURES_OK'`. Если ни то, ни другое не сделано системно, а прогон просто «повезло», критерий хрупкий и может снова не пройти.
2. **Ручное ведение мышью / Автоматика** — на момент диагностики верификация полностью останавливалась из-за недоступности провайдера модели-исполнителя. Стоит убедиться, что финальный done подтверждён настоящим прогоном playwright-сценария с конкретными числами (frame.x у краёв, sample@0.5/2.5/5.5), а не просто тем, что таймаут перестал повторяться.
3. **Точность экспорта** — числовое значение `mean_abs_pixel_diff`, на основании которого сделан вывод о покадровом совпадении с превью, до меня не дошло. Стоит запросить его явно, прежде чем полагаться на признак 8 как на подтверждённый метрикой, а не просто «билд прошёл».

# 7. Следующий шаг

Прогнал бы полный приёмочный набор ещё раз одним чистым проходом (без повторных попыток исполнителя, без падений инфраструктуры), чтобы получить единый протокол с числами по каждому из 9 признаков — включая явное значение `mean_abs_pixel_diff` для точности экспорта и конкретные `sampleTrack`-значения для ручного/автоматического ведения. Отдельно закрыл бы вопрос с фикстурами формально (stderr для лога, а не расчёт на удачный порядок вывода). И дал бы Пилоту ещё один заход на более длинном ролике с двумя говорящими и паузами, чтобы стресс-тестировать признаки 5 и 7 — сейчас у контура 2 есть только одно найденное замечание, и неясно, насколько глубоко он проверял именно поведение автоматики, а не только базовый сценарий загрузки.
