# LOOM v5 — журнал решений

Каждая фаза дописывает раздел: что решено в неочевидном месте, почему именно
так, что осознанно НЕ сделано. Ссылки `§N` — на `LOOM_TZ_v5.md`, если не указано
иное.

---

## Фаза 0 — фундамент (2026-08-05)

- **БД-адаптер:** `core/db.js` пробует `better-sqlite3` первым (`import()`
  внутри `try/catch`), при неудаче — `node:sqlite` (`DatabaseSync`). На машине
  сборки `better-sqlite3` собрался нативно без проблем; фолбэк тем не менее
  проверен вручную (временное перемещение `node_modules/better-sqlite3`) —
  оба бэкенда проходят один и тот же `tests/journal.test.js`, включая гонку
  захвата.
- **BEGIN IMMEDIATE — единственный режим транзакций журнала.** В `db.js` метод
  `transaction(fn)` для better-sqlite3 использует `.immediate(...)` (важно:
  это отдельная вызываемая форма транзакции с теми же аргументами, а НЕ
  модификатор без аргументов — первая попытка `.immediate()` без пробрасывания
  args ломала вызов, поймано тестом `claimNext`). Для `node:sqlite`
  BEGIN IMMEDIATE эмулируется вручную (`exec('BEGIN IMMEDIATE')` /
  `COMMIT`/`ROLLBACK`), так как модуль не даёт готового wrapper'а транзакций.
  Отдельного "deferred" режима в журнале сознательно нет — вся система пишет
  через захват задач, где нужна немедленная блокировка на запись.
- **`claimNext` реализован как SELECT (без блокирующих гарантий) + UPDATE
  внутри одной BEGIN IMMEDIATE транзакции**, а не `UPDATE ... RETURNING`, чтобы
  не зависеть от версии SQLite с поддержкой `RETURNING` в обоих бэкендах.
- **`project_id = 'default'` явно запрещён** в `core/projects.js` /
  `getProject()` (возвращает `null`) — инвариант §13 ТЗ.
- **`io.js`:** один `readline.Interface` на процесс через модульный singleton
  (`sharedInterface`), очередь строк на случай, если несколько мест кода
  вызывают `ask()` подряд. Лимиты 4000/500 символов — обрезка печатает
  предупреждение (не тихая потеря, шрам 16).
## Фаза 1 — шлюз (2026-08-05)

- **Новый Windows-инвариант, не описанный в ТЗ явно (в духе шрама 28):**
  `--tools ""` как ДВА отдельных элемента массива `args` в
  `child_process.spawn(cmd, args, {shell:true})` ломается именно в связке
  Node → `cmd.exe`: внутреннее экранирование Node не оборачивает пустую
  строку в кавычки при сборке командной строки для `cmd.exe`, тот схлопывает
  два подряд идущих пробела, и токен исчезает целиком - следующий флаг
  (`--strict-mcp-config`) подставляется как значение `--tools`, а сам флаг
  strict-mcp-config пропадает. Обнаружено предметно через `argdump.cmd`
  (временный отладочный скрипт, не оставлен в дереве) - воспроизводится и из
  PowerShell, и из Git Bash, то есть баг в Node, не в шелле-вызывающем.
  **Лекарство:** форма `--tools=` (один непустой токен, `commander.js`
  понимает `--flag=value` синтаксис) - даёт тот же эффект (пустой список
  инструментов) и переживает `shell:true` без потерь. Закреплено в
  `core/gateway.js` (`callClaudeCli`) и покрыто тестом
  `tests/gateway.test.js` (проверка `log[0].tools === ''` и
  `log[0].strictMcp === true` одновременно).
- **Цепочка ролей = универсальный механизм и для технических, и для
  содержательных переходов.** ТЗ (§5.2) различает два триггера ("модель упала"
  vs "эскалация на модель сильнее"), но в v1 с единственным провайдером
  (`claude-cli`) оба ведут по одному и тому же списку `ROLES[role]`. Разница
  выражена через `opts.minTierIndex`: `gateway.chat()` сам проходит цепочку
  начиная с индекса 0 при технических сбоях внутри одного вызова; целевая
  content-эскалация (§7: попытка 3 → Opus) - решение `coordinator.js`,
  который на нужной попытке передаёт `minTierIndex` явно. Так гейтвей не
  дублирует логику лестницы попыток, а лестница не дублирует резилиенс к
  падению провайдера.
- **Кривой JSON:** один ретрай на ТОМ ЖЕ тире с добавленным в user-текст
  напоминанием (`[ПОВТОР] ... строго валидным JSON`), затем переход к
  следующему тиру. Технический сбой и `is_error:true` в конверте ретрай на
  том же тире не получают - сразу следующий тир (различие явно проверено
  раздельными тестами).
- **`--tools=`, `--strict-mcp-config`, `--mcp-config`, `--settings` -
  генерируются в `.loom-tmp/` идемпотентно** (`fs.existsSync` перед записью):
  `mcp.empty.json`, `settings.headless.json` - статичные, `sys-<sha256>.txt` -
  по содержимому. Повторный вызов с тем же system-промптом переиспользует файл
  -> условие для кэша промптов claude-cli (проверка в фазе 2).
- **`--bare` НЕ используется** (шрам 29 ТЗ) - подтверждено вручную:
  `claude -p ... --system-prompt-file ... --tools= --strict-mcp-config
  --mcp-config ... --settings ...` работает через подписку без
  `ANTHROPIC_API_KEY` в `.env`.

- **`config.js`: пути, зависящие от `LOOM_HOME`, - функции (`getStateRoot()`,
  `getProjectsDir()`, `getDbPath()`, `getTmpDir()`), НЕ замороженные константы.**
  Обнаружено при написании `tests/pathLock.test.js`: ESM-импорты хостятся и
  выполняются раньше тела любого `test()`, поэтому `process.env.LOOM_HOME = ...`
  внутри теста не мог повлиять на константу, вычисленную один раз при первом
  (транзитивном) импорте `config.js` в процессе. Функции читают `process.env`
  при каждом вызове - изоляция тестов через `LOOM_HOME` (а не MOCK-флаг,
  §19.10 ТЗ) реально работает независимо от порядка импортов. `ROOT` и
  `PROMPTS_DIR` остались константами - они не зависят от `LOOM_HOME`.
- **`core/history.js` (`backupFile`) тоже проходит через `resolveSafePath` и
  тоже логирует нарушение замка пути.** Изначально нарушение логировалось
  только в `pathLock.writeFilesSafely`, но `coordinator.js` вызывает
  `backupFilesBeforeWrite` ДО `writeFilesSafely` - попытка выйти за пределы
  проекта на этапе бэкапа кидала исключение раньше, чем срабатывало логирование
  в `writeFilesSafely`, и `events` оставался пуст для этого случая (поймано
  тестом `tests/coordinator.test.js`, сценарий с `../escape.js`).
- **Auto-commit — безусловный, не "safety net на случай, если Исполнитель
  забыл".** В headless-архитектуре v5 Исполнитель вызывается с `--tools=`
  (инструменты полностью отключены) и физически не может выполнить `git
  commit` сам - у него нет ни одного инструмента, только вывод JSON. Поэтому
  `coordinator.js` коммитит после каждой записи файлов и после каждой проверки
  БЕЗУСЛОВНО, а не по признаку "не закоммитил сам". Git-репозиторий - свой на
  проект (создаётся в `core/projects.createProject`), `cwd` для всех git-команд
  жёстко зафиксирован на каталог проекта (gitGuard, §15.1.4) - утечка в git
  LOOM исключена структурно, а не проверкой.
- **Лестница попыток и тир-эскалация:** попытки 1-2 - `minTierIndex=0`
  (Sonnet), попытка 3+ - `minTierIndex=1` (Opus). "Чистый контекст" на попытке
  2 (§7 ТЗ) не требует отдельной обработки - каждый вызов `coder` уже
  stateless/одноразовый по конструкции (headless claude-cli без `--continue`),
  единственная "память" между попытками - `task.feedback`, который
  `journal.setStatus` перезаписывает, не копит.

## Фаза 2 — Context Engineering (2026-08-05)

- **Счётчик "ходов" и карта хешей файлов персистентны в `projects.context_state`
  (JSON), не в памяти процесса.** Первое реальное применение `ensureColumn` из
  фазы 0. Причина: "любая смерть процесса не должна терять работу" (§2 ТЗ)
  распространяется и на Context Engineering - если бы счётчик хода жил только
  в памяти координатора, `resume` после падения процесса заново показал бы
  "ход 2" (полный снимок) вместо честной дельты, и это не сломало бы
  корректность, но обесценило бы экономию токенов ровно в момент, когда она
  нужнее всего (после многих ходов, кодовая база большая).
- **Дельта считается через SHA-256 хеши содержимого файлов, не через git.**
  Хотя `coordinator.js` коммитит после каждого хода и git-история технически
  могла бы дать тот же diff, завязка на git была бы хрупкой: `gitCommit()` -
  осознанный "safety net", он молча проглатывает ошибки (см. Фаза 1) и может
  не закоммитить, если git недоступен или репозиторий в странном состоянии.
  Хеш-карта в журнале не зависит от git вообще и переживает даже полностью
  отключённый git.
- **Правило "ход ≤ 2 → полный снимок" читается как "ход ≤ 2 ИЛИ ещё нет
  сохранённой карты файлов"** - защита от вырожденного случая (например,
  ручное вмешательство человека стёрло `context_state`, а файлы в workspace
  остались) - тогда система откатывается к безопасному полному снимку вместо
  дельты от пустой карты (которая иначе показала бы КАЖДЫЙ существующий файл
  как "добавленный", что технически верно, но менее читаемо, чем честный
  "полный снимок").
## Фаза 3 — Аналитик и полный вход (2026-08-05)

- **Контракт Аналитика расширен прагматично сверх минимального
  `{route, product_spec_md?, readiness[], engineering_defaults[], questions[]}`
  из гайда:** добавлены `status` (`clarifying|ready` - различает "ещё
  интервью" от "ТЗ готово" в рамках одного и того же `route=build`),
  `project_title` (нужно имя для нового проекта на этапе `ready`), `answer`
  (для `route=question`), `task` (для `route=tweak` - конкретная задача
  Исполнителю без Архитектора), `changed_sections` (для правок). Это не
  нарушает контракт гайда, а уточняет его до реализуемого.
- **Состояние диалога с Аналитиком (транскрипт интервью) живёт в памяти
  процесса `bin/talk.js`, НЕ персистентно.** Персистентно - только РЕЗУЛЬТАТ
  (`product_spec_md` черновик, статус проекта `awaiting_approval`). Если
  процесс убит посреди интервью (ещё не дошли до `утверждаю`), `resume`/новый
  `talk` не восстановит промежуточные вопросы-ответы - интервью начнётся
  заново. Сознательный компромис: то, что человек уже ОТВЕТИЛ, не потеряно
  как факт (это ляжет в новый черновик), а вот сам "переговорный процесс" -
  недорогая вещь, чтобы стоило усложнять журнал ради него в v1.
- **Правка (`правка: <текст>`) - только на этапе `awaiting_verdict`,
  сразу после того, как ТЗ показано человеку.** Слово "правка:" вне этого
  режима - обычный текст, идёт Аналитику как есть (может быть понято как
  `tweak`, если совпадает по смыслу). Отдельного глобального "режима правки"
  нет - это соответствует принципу "одна сессия, Аналитик разбирает сам".
- **Замок дельты правки:** `core/productSpec.js` парсит `product_spec_md`
  СТРОГО по заголовкам `## N. Название` (формат мандатно закреплён в
  `prompts/analyst.md`) и сравнивает секции ПОСИМВОЛЬНО. Нарушение -> одна
  повторная попытка с явным указанием, какие секции тихо поменялись -> если
  снова не сошлось, честный отказ текстом человеку (`отмена` не вызывается
  автоматически - человек решает сам, что делать дальше).
## Фаза 4 — Архитектор и критерии (2026-08-05)

- **Дерево задач вставляется в журнал в два прохода**: сперва все задачи БЕЗ
  зависимостей (чтобы получить реальные `task_<id>` из БД), затем зависимости
  резолвятся из локальных `key` (уникальных только в пределах одного ответа
  Архитектора) в реальные id и дописываются `journal.addTaskDep`. Архитектор
  никогда не видит и не выбирает реальные id - это единственный способ дать
  ему ссылаться на "мою же будущую задачу X" до того, как она создана.
- **Регрессия - роль `coder`, но `coordinator.processTask` перехватывает её ДО
  вызова Исполнителя** (`task.criteria.regression_of` → `processRegressionTask`):
  Coder не вызывается вообще, сразу Проверяющий повторяет существующие
  критерии done-задач. Провал регрессии не уходит в лестницу попыток (нечего
  чинить кодом - это сигнал тимлиду, не Исполнителю).
- **`npmInstallGuarded` - `npm prefix` ДО `npm install`, cwd жёстко = каталог
  проекта.** Протестировано и синтетически (ancestor package.json без
  собственного - guard кидает ошибку ДО реального `npm install`), и в
  реальном прогоне (пакеты действительно ставятся в `projects/<id>/node_modules`,
  `package-lock.json` создаётся на месте, LOOM-репо не тронут).
- **Трассировка `covers` - точное строковое совпадение с `readiness[]`,
  и это оказалось СЛИШКОМ строгим на практике.** В реальном прогоне Архитектор
  почти всегда слегка перефразирует признак готовности в `covers`, из-за чего
  `uncoveredReadiness` показывает почти все пункты как "непокрытые", хотя по
  смыслу они закрыты. Механизм оставлен как есть (он информационный, не
  блокирующий - решение читает человек), но точное совпадение строк - известное
  ограничение v1; v2 стоит рассмотреть нечёткое сравнение или явное указание
  Архитектору дословно копировать список `readiness` перед `covers`.
- **Обнаружено вживую (не шрам ТЗ, но кандидат в реестр): `claude` может
  само-обновиться ПОСЯДИ сессии** (версия сменилась 2.1.220 → 2.1.222 в
  процессе тестирования Фазы 4), вызвав кратковременные `ENOENT`/"batch file
  cannot be found" на паре вызовов. Шлюз классифицировал это ровно как
  техническую ошибку (`isTechnicalFailure`) и корректно продолжил
  цепочку/круги - тот же механизм, что защищает от "все модели недоступны
  в час пик" (шрам 13), без правок кода отработал и на этот класс сбоя.
- **Обнаружено вживую: `planProject` не идемпотентен.** Если процесс убит
  ПОСЕРЕДИНЕ планирования/выполнения дерева и `planProject` вызван повторно
  для того же проекта, создаётся ВТОРОЕ дерево задач поверх первого (в отличие
  от `Coder`, для которого `releaseStuck` + `claimNext` дают полную
  идемпотентность возобновления). Это не ломает корректность (оба дерева
  выполнимы независимо), но создаёт дублирующиеся/конкурирующие файлы.
  Зафиксировано как известное ограничение v1: `bin/talk.js` вызывает
  `planProject` ровно один раз за подтверждение `утверждаю` в штатном потоке,
  и это единственный путь его вызова - на практике повторный вызов возможен
  только через ручное вмешательство в код/БД, как при отладке этой фазы.
## Фаза 5 — Дизайнер и HeroUI-документация (2026-08-05)

- **Гейт "вызывать ли Дизайнера" решает Аналитик, не Архитектор** - добавлено
  поле `domain` в контракт Аналитика (`prompts/analyst.md`), проставляется в
  `projects.domain` в момент создания/обновления product_spec. Причина: по
  диаграмме §3 ТЗ Дизайнер идёт ДО Архитектора, а Архитектор в нашей
  реализации узнаёт домен только из СВОЕГО собственного ответа - кто-то должен
  решить ДО Архитектора, нужен ли вообще визуальный интерфейс. Архитектор
  может проставить `domain` повторно (финальное слово по стеку - его), но
  решение "звать ли Дизайнера" принято раньше и от него не зависит.
- **`core/herouiDocs.js` реально ходит в сеть** (`https://www.heroui.com/react/llms.txt`,
  проверено вручную - это настоящий, работающий индекс документации HeroUI v3,
  ~44К символов), с диск-кэшем на 24ч и ЧЕСТНОЙ деградацией (сеть недоступна
  И кэша нет -> явная строка "документация недоступна", а не тишина или
  выдумка). URL проверен вручную перед вшиванием в код, не угадан.
- **Направление дизайна - отдельный режим сессии
  (`awaiting_design_direction`), в памяти процесса, не персистентный** - та же
  осознанная граница, что и для интервью product_spec (Фаза 3): если процесс
  убит между показом 2-3 вариантов и выбором человека, `talk.js` при
  перезапуске НЕ восстановит показанные варианты (подтверждено вживую - "2"
  после перезапуска ушло в Аналитика как обычный текст, не как выбор
  направления). Обход - прямой вызов `runDesigner({..., chosenDirection})`
  в крайнем случае; штатный путь не пересекает границу процесса.
- **Обнаружено вживую и ИСПРАВЛЕНО (важная находка, не мелочь): простого
  упоминания "используй только эти токены" в промпте Исполнителя НЕДОСТАТОЧНО.**
  В первом реальном прогоне (лендинг «Аврора», направление «Полярный рассвет»)
  Исполнитель на всех 4 попытках проигнорировал реально переданную
  дизайн-систему (8059 символов в user-контексте, подтверждено логами) и
  сочинил СОБСТСТВЕННУЮ тёмную hex-палитру под другими именами переменных.
  Причина, по-видимому, - недостаточно императивная формулировка правила
  среди прочих инструкций. **Исправлено на двух уровнях** (§18 ТЗ, правильный
  уровень - Prompt, не Harness, потому что harness ничего не делает
  неправильно - критерия на это просто не было):
  1. `prompts/coder.md` - правило переписано как жёсткое требование СКОПИРОВАТЬ
     блок `:root` из `tokens.css` дословно и использовать только `var(--...)`;
  2. `prompts/architect.md` - добавлено ОБЯЗАТЕЛЬНОЕ требование включать в
     дерево критерий, буквально считающий hex-литералы в выходных HTML-файлах
     (`expect:{"equals":"0"}`) - это ровно требование DoD Фазы 5 из гайда
     ("нет захардкоженных hex там, где есть токен"), которое отсутствовало
     до этой находки.
  Исправление проверено изолированным реальным вызовом Исполнителя (не полным
  прогоном ради экономии) - результат: 0 hex-литералов, 20 использований
  `var(--token)`, включая дословно скопированный блок `:root`.
- **Playwright требует ОТДЕЛЬНОЙ загрузки браузера** (`npx playwright install
  chromium`) сверх `npm install playwright` - реальный сбой первого прогона
  Пилот-подобного (DOM-based) критерия был именно этим, не багом гейтвея/
  координатора. Это чисто инфраструктурный шаг машины, на которой развёрнут
  LOOM - не часть кода продукта, но стоит явно прописать в `README.md` LOOM
  как предусловие перед Фазой 6 (Пилот) и первым UI-проектом.
## Фаза 6 — Пилот, второй контур (2026-08-05)

- **Пилот пишет Node-скрипт, харнесс его исполняет - как Архитектор пишет
  критерии, а Проверяющий их исполняет.** Ключевая архитектурная развилка
  этой фазы: у Пилота (LLM) в headless-модели НЕТ инструментов (`--tools=`,
  как у всех ролей), поэтому он физически не может сам покликать браузер.
  Решение: Пилот возвращает JSON `{"script": "..."}` (содержимое `.cjs`,
  пишется harness'ом напрямую в файл - без shell-квотирования вообще, в
  отличие от критериев Архитектора, потому что здесь harness сам управляет
  записью файла, а не встраивает код в команду), затем harness запускает
  `node <файл>` и разбирает РОВНО одну JSON-строку из stdout как находки.
  Это не имитация "Пилот пользуется продуктом" - реальный процесс на диске
  реально исполняется, реально может упасть, и его провал не маскируется.
- **`ensurePlaywrightPackage`/`checkBrowserAvailable` вызываются ТОЛЬКО при
  `domain==='ui'`.** Первая версия проверяла браузер всегда, что означало
  реальный `npm install playwright` по сети для КАЖДОГО cli/lib/data-проекта
  (обнаружено по аномально долгим тестам - ~2с на тест вместо ~0.3с).
  Инвариант стоимости (§1.2 ТЗ - тот же принцип, что "Дизайнер не вызывается
  для не-UI", применённый к Пилоту).
- **Обнаружено вживую: Пилот, даже имея реально установленный и доступный
  браузер, иногда всё равно выбирает текстовый regex-анализ HTML вместо
  Playwright** - и один раз это дало ЛОЖНОЕ срабатывание (искал
  `class="card"`, а реальная разметка использовала `data-card` как атрибут -
  Пилот честно написал `visual:false` и создал `blocker`-находку "карточек
  0", хотя карточки реально были). Исправлено ЧАСТИЧНО на уровне промпта
  (`prompts/pilot.md` - явное указание "браузер доступен -> ОБЯЗАН
  использовать Playwright, текстовый анализ - только для реальной
  деградации"). Повторный реальный прогон после правки: находок 0 (ложного
  срабатывания больше нет), но `visual` всё ещё `false` - модель
  по-прежнему консервативно недооценивает как "визуально не проверено".
  **Это приемлемо и оставлено как есть**: система по духу ТЗ (§8.5, "никогда
  не имитировать") должна скорее НЕДО-заявлять уверенность, чем ПЕРЕ-заявлять
  её - недооценка честности не создаёт риска, переоценка создаёт.
- **`applyPilotFindings` не различает blocker/major/minor на уровне
  ИСПОЛНЕНИЯ** - все находки становятся обычными `coder`-задачами
  `type=pilot_fix` и проходят одну и ту же лестницу попыток. Различие
  blocker/major/minor - для ЧЕЛОВЕКА при сдаче (Консультант, Фаза 8):
  `hasBlockers()` определяет, можно ли считать проект сданным. Уровень
  проверки задачи (§8) от severity находки не зависит - критерий есть
  критерий.
## Фаза 7 — Диагност и лестница честности (2026-08-05)

- **"Уже консультировались с Диагностом" - не отдельный счётчик, а вывод из
  существующего состояния задачи**, чтобы не раздувать схему:
  - уровень `code`: `attempts` НЕ сбрасываются при редиректе -> вторая
    эксхаустия (`attemptNumber > MAX_ATTEMPTS`) однозначно значит "подсказка
    не помогла";
  - уровни `approach`/`understanding`: `attempts` сбрасываются в 0 (свежая
    лестница под новый подход/формулировку), но `task.level` перестаёт быть
    `'code'` -> вторая эксхаустия опознаётся по `level`, не по числу попыток.
  Это даёт ровно ОДИН цикл смены уровня на задачу (шрам 17: "упорные" попытки
  не должны становиться бесконечными), без отдельной колонки-счётчика.
- **Измерение (`measurement_request`) реально исполняется** через
  `checkRunner.runSingleCheck` (тот же путь, что критерии Архитектора) - НЕ
  отдельная задача `type=tool` на доске, как буквально написано в гайде
  (§9 Фазы 7 гайда), а прямой синхронный вызов внутри `runDiagnosticianLadder`.
  Осознанное упрощение: полноценная задача на доске потребовала бы либо
  синхронного захвата вне `claimNext` (нарушает модель "одна задача - один
  claim"), либо приостановки всей лестницы до следующего цикла координатора.
  Факт всё равно пишется в `events` (`kind:'measurement'`) - наблюдаемость
  сохранена, просто без промежуточной строки в `tasks`.
- **`approach` персистентен в `projects.approach_json`** (новая колонка через
  `ensureColumn`) - без этого Диагност не мог бы предложить "другой вариант
  из `approach.options`", так как сам список вариантов существовал только в
  возвращаемом значении `planProject()` и нигде не сохранялся до этой фазы.
- **Реальная проверка (не по фейковой модели): task_6ab7485d43 из Фазы 4**
  (провал 4/4 попытки - Исполнитель генерировал `package.json` с настолько
  плотным экранированием JSON-внутри-JSON, что ответ обрывался на середине)
  был вручную возвращён в очередь для повторного прохода лестницы. Реальный
  Диагност поставил диагноз **level=code** с точной, ранее не
  сформулированной причиной: "проблема в объёме/форме выдаваемого кода... нужно
  выдать минимальные по объёму файлы" - и это ТОЧНО совпало с гипотезой,
  записанной в этом документе при разборе Фазы 4. Задача решилась на
  следующей попытке (`attempts` итого 5, `level=code`, `status=done`).
  Это лучшее доказательство того, что "свежий взгляд" (роль отдельная от
  автора кода) реально работает не только по конструкции, но и на практике.
- **Обнаружен и исправлен реальный дефект теста (не продакшн-кода):**
  последний тест `tests/pilot.test.js` вызывал `createJournal()`/`createProject()`
  БЕЗ `setupTestEnv()` - писал прямиком в боевой `journal.db` LOOM и создавал
  реальные каталоги в `projects/`. За несколько прогонов полного набора тестов
  накопилось 5 паразитных проектов "Pilot Findings" в реальном журнале.
  Исправлено (обёрнуто в `setupTestEnv`/`try-finally`), паразитные записи и
  каталоги вручную удалены. Урок: контрольный список ревью (§15 гайда) уже
  требует "`npm test` зелёный" - стоит добавить туда же явный пункт "каждый
  `test()`, трогающий `createJournal`, обёрнут в `setupTestEnv`", раз ручная
  проверка одного пропущенного теста заняла отдельный проход.
## Фаза 8 — Консультант и сдача (2026-08-05)

- **Пункт 8 ("Расход") никогда не проходит через модель.** `agents/consultant.js`
  вызывает LLM только за пунктами 1-7 (`json:false` - обычный markdown-текст,
  не структурированный JSON, потому что это отчёт для человека, не контракт
  для harness), затем harness буквально дописывает результат
  `core/stats.formatSpendReport()` - чистый SQL по `events`, ни одного
  вызова модели, числа невозможно сгенерировать неверно, потому что их не
  генерирует LLM вообще.
- **`REPORT.md` пишется harness'ом напрямую** (`fs.writeFileSync`, не через
  `pathLock.writeFilesSafely`/контракт Исполнителя) - Консультант не
  Исполнитель, у него нет проверки по `touches_files`, а корень проекта
  (не поддиректория) для отчёта - осознанное решение, отчёт должен быть
  на виду, а не спрятан внутри `src/`.
- **Финальный статус проекта (`delivered` vs `active`) решает наличие
  `blocked_needs_human` ЛИБО blocker-находок Пилота ЛИБО незелёной доски** -
  простое булево правило в `bin/talk.js`, не решение самого Консультанта
  (Консультант описывает ситуацию человеку, статус в БД - механический факт,
  не мнение LLM).
- **Реальный прогон на уже сданном проекте "Лендинг Аврора" дал по-настоящему
  полезный, неожиданный результат:** Консультант САМ заметил (не была
  подсказана явно), что первая задача дерева в своё время прошла через
  диагностическую историю (лестница попыток была задействована при более
  раннем ручном тестировании Фазы 5/6), и явно вынес это в раздел 5 ("Что
  хромает") как риск, требующий ручной перепроверки контента - хотя формально
  задача имеет статус `done`. Также корректно (по данным `events`, а не по
  памяти о том, что автор сессии где-то руками гонял Пилота отдельным
  скриптом мимо `bin/talk.js`) сообщил, что Пилот "не запускался" для этого
  прогона - отчёт строится СТРОГО из журнала, не из общего "ощущения", что
  проект вроде бы проверен.
- **НЕ сделано осознанно:** `ensureColumn` реализован как утилита, но пока не
  вызывается — схема строится с нуля через `CREATE TABLE IF NOT EXISTS` с уже
  финальным набором колонок. Она понадобится при первой реальной миграции схемы
  после релиза v1.
