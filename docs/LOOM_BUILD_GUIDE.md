### 0.1. Точки входа — ровно две

```
npm run talk      всё общение по проектам: строй / спроси / поправь.
                  Тип запроса определяет Инженер (§1.1, режим «Понимание»), не человек.
npm run resume    поднять доску и доработать после перерыва или падения.
                  Это команда процессу, а не сообщение LOOM — классифицировать нечего.
```

Команды внутри сессии `talk`:
`/status` · `/projects` · `/project <id>` · `/exit`

> **Третьей команды («задать вопрос») быть не должно.** Инженер сам различает
> `build | question | tweak` первым же вызовом. Отдельный вход дублировал бы
> эту работу и заставлял человека классифицировать свой запрос вручную.
> Канал `/mentor` убран вместе с ролью (§12 ТЗ) — не «временно скрыт», а
> реально отсутствует в коде до тех пор, пока роль не вернётся отдельной
> задачей.

## 1. Ключевые контракты кода (не менять без правки ТЗ)

**Шлюз:**
```
chat(role, messages, {json?, projectId?, taskId?, runId?}) → текст | объект
```
Ошибка / таймаут / не-JSON = сбой модели → следующая в цепочке; два круга (§5.2).
`role` — один из `engineer | coder | pilot | diagnostician`. Режим Инженера
(«Понимание»/«Дизайн-направление»/«План»/«Сверка целого»/«Сдача») различается
заголовком `# Режим: ...` в user-сообщении, не отдельной ролью в цепочке.

**Журнал:**
```
createProject({title, domain}) → project
addTask({project_id, title, spec, criteria, role, type, touches_files, covers, deps, core_check})
claimNext(role, projectId) → task | null       // BEGIN IMMEDIATE
setStatus(id, status, {feedback?, question?})  // feedback ПЕРЕЗАПИСЫВАЕТСЯ; status может быть 'retired'
releaseStuck()                                  // при КАЖДОМ входе
logEvent({run_id, project_id, task_id, type, agent, ...})  // type включает 'checkpoint'
```

**Критерий:** `{cmd, expect, timeout_ms?}` либо `{regression_of:[taskIds]}`.
Исполняет только `runCheck(cmd, {cwd, timeout})`; `node -e` выносится в
`.loom-check-<rand>.cjs` **внутри workspace проекта**.

**Исполнитель:** вход = `system(prompts/coder.md)` + `user(задача + product_spec-цель + дизайн-система + дельта файлов + последний feedback)`;
выход **строго** `{"files":{path:content}}` | `{"question":"..."}`;
запись — harness'ом, только под `projects/<id>/`.

**Инженер, режим «Понимание»:** выход `{route, product_spec_md?, readiness:[{text,tier}], core_intent?, engineering_defaults[], questions[]}`.
Ошибка парсинга → `route='build'`.

**Координатор:** `runLoopWithCheckpoints({journal, project, productSpec, ...})`
— как обычный цикл `claimNext → processTask`, но между задачами вызывает
`runCheckpoint` по правилам §3.2; `canDeliver({project, productSpec, tasks,
pilotResult})` — гейт сдачи без LLM (core-признаки, `visual:false`, связность
токенов).

`core/db.js`, `core/journal.js`, `core/projects.js`, `core/io.js`,

  `node --env-file=.env --no-warnings <bin>`.
- `core/db.js`: пробуем `better-sqlite3`, при ошибке сборки — `node:sqlite`
  (`DatabaseSync`). `PRAGMA journal_mode = WAL`.
- `core/journal.js`: схемы §4 целиком (`projects`, `product_spec` с

  `type='checkpoint'`, `lessons` — оставлена, не используется), индексы,
  идемпотентный `ensureColumn` (SQLite не умеет `ADD COLUMN IF NOT EXISTS` —

- `core/io.js`: один `readline`, очередь строк, санитизация (ANSI/control),
  лимит **4000** символов для содержательного ввода / 500 для команд;
  обрезка печатает предупреждение, не молчит.

**DoD:** создание проекта и задачи из CLI работает; два параллельных процесса
не выдают одну задачу дважды (`tests/journal.test.js` — гонка захвата);
`releaseStuck` возвращает `claimed` в `pending`.

## 3. Фаза 1 — шлюз и один агент по-настоящему (дни 2–4)

**Файлы:** `core/gateway.js`, `core/checkRunner.js`,
`core/pathLock.js`, `core/history.js`, `core/coordinator.js`,
`agents/coder.js`, `agents/checker.js`, `prompts/coder.md`, `bin/talk.js` (минимум).

**Порядок:**
1. **Руками:** `claude -p "скажи ok" --output-format json` работает в терминале.
   Не работает — дальше не идти.
2. `gateway.js`: сборка аргументов (§5.1), system-промпт файлом с именем
   `sys-<sha256>.txt`, user через STDIN, `child.stdin.on('error')` глотает
   EPIPE. Разбор конверта: `{result, is_error, total_cost_usd, usage:{...}}`.
   `usage` → `events`. Цепочки + два круга + таймаут.
3. `pathLock.js` — **с первого дня**, не позже: любая запись вне
   `projects/<id>/` блокируется и логируется.
4. `history.js` — бэкап перед каждой правкой файла.
5. `checkRunner.js`: `node -e` → `.cjs` внутри workspace; таймаут по классу
   (§8.8); отчёты 1000 символов; серверный шаблон (§8.6).
6. `coordinator.js`: `releaseStuck()` на старте → цикл
   `claimNext → coder → checker → вердикт`; лестница §7 без Диагноста (просто
   `attempts`); auto-commit в конце хода.
7. `coder.js`: глаза = **полный снимок** (дельта — фаза 2), фильтр мусора
   **сразу** (`.min`, >50КБ, бинарники).

**Реальный прогон (обязателен):** задача вручную, без Инженера —
`«sum.ts: экспортирует sum(a,b)»`, критерий
`node -e "require('./dist/sum.js').sum(2,3)===5"`. Цель фазы — конвейер
задача → код → проверка, не диалог.

**DoD:** прогон зелёный; в `events` есть `run_id`, `usage`, длительности;
попытка записи `../evil.ts` заблокирована и видна в журнале.

## 5. Фаза 3 — Инженер: Понимание и полный вход (дни 7–10)

**Файлы:** `agents/engineer.js` (режим «Понимание»), `prompts/engineer.md`
(раздел «Режим: Понимание»), `bin/talk.js` (полностью), `bin/resume.js`.

- Классификация входа: `build | question | tweak`; при неуверенности → `build`.
- **regex-фильтр технических вопросов кодом** (§1.1.1) — без `\b`, с логом
  срабатываний в `events`.
- `product_spec` в журнал, включая `core_intent` и `readiness:[{text,tier}]`;
  **точка утверждения** (`утверждаю` / `правка:` / `отмена`) — сверка ядра
  замысла с человеком часть этой точки; при `правка:` — сверка, что нетронутые
  пункты дословны.
- `talk.js`: команды `/status /projects /project /exit`; `unhandledRejection`-
  броня; санитизация ввода.
- Статус проекта `awaiting_approval` — чтобы `resume` подхватил после
  перерыва.

**Реальные прогоны (все маршруты):**
- `question`: «что делает src/sum.ts?» → ответ, **ноль записей** в задачи;
- `tweak`: «переименуй экспорт sum в add» → одна задача, done;
- `build`: «одностраничник: заголовок, три карточки, тёмная тема» →
  `product_spec` (с ядром замысла) → утверждаю → 3–5 задач + регрессия →
  открывается в браузере.

**DoD:** в стенограмме интервью **нет ни одного технического вопроса**;
`product_spec` содержит все восемь разделов, включая ядро замысла; правка
меняет только адресованное.

## 6. Фаза 4 — Инженер: План, критерии, дизайн-направление (дни 11–16)

**Файлы:** `agents/engineer.js` (режимы «Дизайн-направление» и «План»),
`prompts/engineer.md` (соответствующие разделы), `core/herouiDocs.js`,
`core/tokenCheck.js`.

**План (было — Архитектор):**
- `prompts/engineer.md` (режим «План») = **свод §8 дословно, включая правила
  11-13** + требование блока `approach` с минимум двумя вариантами для
  нетривиальных задач + `riskiest_assumption`, если достижимость core-признака
  неочевидна.
- `packages` → `npm install` **строго после** создания
  `projects/<id>/package.json`; guard: `npm prefix` в `cwd=projectDir` обязан
  совпасть с `projectDir`, иначе установка отменяется с явной ошибкой (шрам 36).
- Предпроверки (§8.9 + новые): тихий прогон критериев на пустом workspace
  (фиктивность), синтаксическая проверка `node -e` тел (обрыв генерации),
  heuristика слабых UI-критериев (правило 11) — каждая с логом и ОДНОЙ
  регенерацией.
- Контракт регрессии (§8.10): склейка **существующих** id, не генерация новой
  проверки.
- `covers`: каждый признак готовности из `product_spec` покрыт; непокрытый —
  сообщить человеку до старта. Каждый `core`-признак дополнительно покрыт
  хотя бы одной `core_check`-задачей — непокрытый логируется отдельно
  (`kind='uncovered_core_check'`).
- Таймауты критериев по классу — **в коде** (`checker`), поле `timeout_ms` в
  плане — опционально поверх.

**Дизайн-направление (было — Дизайнер, теперь режим того же Инженера):**
- Соответствующий раздел `prompts/engineer.md` = **свод §10 дословно**,
  включая правило против усреднения.
- Домен определяется один раз (`projects.domain`); `domain !== 'ui'` → режим
  «Дизайн-направление» **не вызывается вовсе**.
- Выход → `projects/<id>/design/tokens.css` + `DESIGN.md`; Исполнитель
  получает этот блок **всегда полностью**.
- `herouiDocs.js`: подтягивание актуальной документации HeroUI (llms.txt/MCP)
  в user-контекст. Версия — из `HEROUI_VERSION` (запинена).
- Направление: если человек дал референс — используется он; иначе Инженер
  предлагает 2–3 направления, человек выбирает одним словом.

**Связность токенов (`core/tokenCheck.js`, правило 12, шрам 40/41):**
- `checkTokenConnectivity(projectDir)` — читает `design/**/*.{css,html}` на
  объявленные `--токены` и все остальные `.css`/`.html` продукта на
  использованные `var(--x)`; несовпадение → `{pass:false, undefinedTokens,
  report}` со списком.
- Вызывается **harness'ом на гейте сдачи** (`coordinator.canDeliver`), не
  задачей в дереве — код-уровневый гейт устойчивее, чем полагаться на то, что
  Инженер не забудет вписать критерий в план.

**DoD:** дерево из 5+ задач; предпроверки печатают строку на каждое
срабатывание; регрессия — повтор существующих; сгенерированный интерфейс
использует **только** токены (искусственно испорченный `tokens.css` даёт
`checkTokenConnectivity` непустой список); контраст ≥ 4.5:1; раскладка не
ломается на 375px; при `domain=cli` дизайн-вызовов и токен-гейта ноль.

## 7. Фаза 5 — Пилот, второй контур (дни 17–19)

**Файлы:** `agents/pilot.js`, `prompts/pilot.md`.

- Запускается **после зелёной доски**, один цикл на сдачу.
- Инструменты: Playwright (клики, drag, ввод, чтение позиций элементов) +
  программные проверки (`ffprobe`, парсеры).
- Первый шаг для `domain='ui'` — проверка жизни страницы (правило 11); не
  отрисовалась → `blocker`, остальной сценарий не имеет смысла.
- Сценарий берётся из `product_spec` раздел «Как работает» — Пилот проходит
  его **целиком, как пользователь**, и печатает `steps_done` — реально
  пройденные шаги, не только `findingsCount`.
- Находки → задачи `type=pilot_fix` с готовыми критериями; `blocker`
  блокирует сдачу.
- **Деградация обязательна, но с последствием:** нет браузеров → работает по
  доступным программным проверкам и **честно помечает** `visual:false`. Для
  `domain='ui'` это **блокирует сдачу целиком** (`requiresVisualBlock`, §9,
  шрам 42) — не просто пометка в отчёте.

**DoD:** на тестовом проекте Пилот находит ≥1 реальную проблему со `steps_done`
в выводе, она превращается в задачу, задача закрывается, повторный прогон
чистый; искусственно смоделированный `visual:false` на `domain='ui'`
блокирует `canDeliver`.

## 8. Фаза 6 — Диагност и лестница честности (дни 20–22)

**Файлы:** `agents/diagnostician.js`, `prompts/diagnostician.md`.

- Включается на попытке `MAX_ATTEMPTS` (4, или `SPIKE_MAX_ATTEMPTS`=3 для
  `type=spike`, §7). **Не та роль, что писала код.**
- Определяет уровень: `code | approach | understanding` → пишет в `tasks.level`.
  - `approach` → Инженер (режим «План») перепроектирует ветку, взяв **другой
    вариант** из сохранённого `approach.options`;
  - `understanding` → сверка с `product_spec`, перепостановка задачи.
- Заказывает **измерения** — изоляция причины фактом, не догадкой.
- Исчерпал уровни → `blocked_needs_human` с диагнозом по шаблону §11 (шесть
  пунктов) + **частичный работающий результат**.

**DoD:** искусственно сломанная задача (заведомо неверный подход) проходит
`code → approach` и чинится сменой подхода, а не десятью попытками на одном
уровне; в `events` виден переход уровня; spike-задача уходит на диагноз после
3 попыток, не 4.

---

## 9. Фаза 7 — Сверка целого (checkpoint) (дни 23–25)

**Файлы:** `core/coordinator.js` (`runLoopWithCheckpoints`, `canDeliver`),
`agents/engineer.js` (`runCheckpoint`, `applyCheckpointActions`),
`prompts/engineer.md` (раздел «Режим: Сверка целого»).

- Координатор вызывает Инженера между задачами по правилам §3.2: каждая
  третья `done`, обязательно после `core_check`-задачи, обязательно после
  `blocked_needs_human`.
- `on_track:false` → конвейер останавливается **до** следующей задачи;
  `actions` (`add_task`/`retire_task`/`revise_criteria`/`revise_plan`)
  применяются немедленно; `retire_task` не имеет права трогать уже `done`.
- Каждая сверка — запись `events.type='checkpoint'`, видимая в отчёте.
- `canDeliver` — код-уровневый гейт сдачи: неподтверждённый `core`-признак
  (правило 13), `blocked_needs_human`-задачи, `visual:false` для `domain='ui'`
  (шрам 42), нарушенная связность токенов (правило 12, фаза 4) — любое из
  этого не даёт статус `delivered`.

**DoD:** искусственный сценарий с `on_track:false` останавливает
`runLoopWithCheckpoints` до выполнения следующей задачи; `actions:
[add_task]` добавляет и в этом же прогоне выполняет новую задачу;
`canDeliver` с неподтверждённым `core`-признаком возвращает `ok:false` с
объяснением.

## 10. Фаза 8 — Разведка (spike) (дни 26–28)

**Файлы:** `agents/engineer.js` (`planProject` — создание spike-задачи),
`core/coordinator.js` (`maxAttemptsForTask`), `prompts/engineer.md` (раздел
«Задача 2» режима «План»).

- Если `approach.riskiest_assumption` присутствует, harness создаёт задачу
  `type=spike` **первой** и добавляет её как `blocked_by` всем остальным
  задачам дерева (build-задачам и регрессии).
- Разведзадача не строит продукт — голый `node -e` скрипт из
  `riskiest_assumption.how_to_check`, печатающий числа.
- `SPIKE_MAX_ATTEMPTS=3` — меньше общего `MAX_ATTEMPTS=4` (§7).
- Исход интерпретируется на ближайшей сверке целого (§3.2, фаза 7) — она
  срабатывает обязательно, т.к. spike либо закрывается (нет специального
  триггера), либо уходит в `blocked_needs_human` (триггерит checkpoint по
  этому правилу).

**DoD:** дерево с `riskiest_assumption` — первая `claimable`-задача именно
spike, остальные заблокированы; закрытие spike разблокирует дерево; провал
spike-задачи уходит на Диагноста после 3, не 4, попыток.

## 11. Фаза 9 — Сдача: отчёт Инженера (дни 29–30)

**Файлы:** `agents/engineer.js` (режим «Сдача»), `prompts/engineer.md`
(раздел «Режим: Сдача»), `core/stats.js`.

- Отчёт по **девяти** пунктам §17 (было семь+расход, теперь плюс ядро замысла
  и «что НЕ проверено»), включая блок `approach` (что рассматривали, что
  выбрали, почему, исход разведки) — человек должен видеть, что система
  **думала**, а не просто закрывала тикеты.
- `core/stats.js` — отчёт о расходе (§17.1). Это **чистый SQL по `events`**,
  без вызовов модели:
  ```sql
  -- по ролям
  SELECT agent, COUNT(*) calls, SUM(tokens_in) tin, SUM(tokens_out) tout,
         SUM(cache_read) cached, ROUND(SUM(cost_usd),2) cost,
         SUM(duration_ms) ms
  FROM events WHERE project_id = ? AND type = 'usage'
  GROUP BY agent ORDER BY cost DESC;

  -- календарное время
  SELECT MIN(created_at) first, MAX(created_at) last
  FROM events WHERE project_id = ?;

  -- качество: распределение по попыткам
  SELECT attempts, COUNT(*) FROM tasks
  WHERE project_id = ? AND status = 'done' GROUP BY attempts;
  ```
  Роли **без** вызовов модели (`checker`) в таблицу не попадают — это
  правильно, они бесплатны.
- `README.md` продукта — часть поставки, генерируется как обычная задача.
- Поставка = `projects/<id>/` + README + отчёт, но **только если**
  `canDeliver` (фаза 7) вернул `ok:true`. Публикация не входит в v1.

**DoD:** отчёт отвечает на «что просил / ядро замысла / что решил и почему /
как проверено / что НЕ проверено / что хромает / что требует меня»; раздел
«что НЕ проверено» не пуст фразой без факта; таблица расхода сходится —
сумма по ролям равна общей стоимости прогона; календарное время ≥ времени
работы.

## 12. Фаза 10 — ЭКЗАМЕН (§22)

**Полный прогон видео-проекта без вмешательства в разработку.**

1. `npm run talk` → описание из §22 → Инженер: Понимание → `product_spec` с
   ядром замысла → утверждаю.
2. Инженер: Дизайн-направление → направление → Инженер: План (обязан
   рассмотреть ≥2 варианта автослежения и выделить `riskiest_assumption` для
   разведки, §3.3) → разведка → дерево → сборка со сверками целого (§3.2).
3. Пилот проходит все 10 признаков готовности, `visual:true`, `steps_done`
   непустой.
4. Отчёт Инженера (девять пунктов).

**Критерий сдачи экзамена (release-критерий v1.0).** LOOM v1.0 считается
работающим, когда на чистой машине по README:

1. три маршрута (`question`/`tweak`/`build`) отрабатывают на живых моделях;
2. видео-проект собирается end-to-end **без вмешательства человека в
   разработку** — только описание, утверждение ТЗ и финальная приёмка;
3. признаки готовности 1–7 (база) закрыты и подтверждены Пилотом фактами;
4. признаки 8–9 (метрики автослежения) **измеряются и показываются** — даже
   если качество слежения пока слабое (это прогресс, а не провал, §22);
5. убийство процесса в любой точке не теряет работу — `resume` доводит;
6. отчёт Инженера отвечает на «что / ядро / почему / как проверено / что не
   проверено / что дальше»;
7. `git diff` в репозитории LOOM после прогона **пуст** (продукт не загрязнил
   машину, шрам 36);
8. хотя бы одна сверка целого (`checkpoint`) зафиксирована в `events`;
9. `canDeliver` вернул `ok:true` до того, как проект получил статус
   `delivered` — не по словам отчёта, а по факту гейта.

Пункты 1–9 — и только они — определяют готовность v1.0. Всё остальное —
развитие. Наставник и постоянная память **сознательно не входят** в этот
список (§12/§23 ТЗ) — они отложены, не забыты.

## 13. Тесты машины (без MOCK-режима)

**Принцип: продакшн-код ничего не знает о тестах.** Ни одного `if (MOCK)`,
ни одного `if (TEST)`.

**Механизм — подставной `claude` в PATH.** `gateway.js` вызывает `spawn('claude')`
по имени → тест кладёт в PATH свой исполняемый файл, который читает STDIN и
печатает такой же JSON-конверт. Продакшн-код идёт **полностью настоящим путём**:
сборка аргументов, файл системного промпта, STDIN, разбор конверта, `usage`,
фолбэки, два круга, ретрай на кривом JSON.

**Изоляция состояния — `LOOM_HOME`,** не булев флаг: тест выставляет
`LOOM_HOME=<tmpdir>/loom-test-<pid>` и получает свой мир (своя БД, свои
`projects/`). Не задан — работает живой режим.

**Заглушка обязана уметь ломаться по заказу:** `is_error`, невалидный JSON,
`exit 1`, зависание дольше таймаута. Иначе фолбэки, два круга и ретрай не
проверены **ничем**.

**Покрытие (`npm test`, `--test-concurrency=1`):**
`gateway` (конверт, usage, кэш, фолбэк-цепочка, два круга, кривой JSON,
таймаут) · `journal` (гонка захвата, зависимости, `releaseStuck`) ·
`coordinator` (лестница попыток, замок пути, auto-commit, checkpoint-цикл,
`canDeliver`, `SPIKE_MAX_ATTEMPTS`) · `projects` (изоляция двух проектов) ·
`checkRunner` (`.cjs`-вынос, таймаут по классу) · `engineer` (regex-фильтр,
классификация, план с `core_check`/spike/предпроверками, checkpoint, отчёт) ·
`tokenCheck` (связность токенов, честный список необъявленных имён) ·
`pilot` (`steps_done`, `requiresVisualBlock`) · `diagnostician` (переход
уровня).

## 14. Правила разработки LOOM с помощью Claude Code

1. **Шаблон промпта:** контекст (2–3 строки + «прочитай файлы X, Y») → проблема
   с историей ПОЧЕМУ (шрам/инцидент) → что сделать по пунктам → что **не**
   трогать → как проверить.
2. **Один промпт = одна зона** (шлюз ИЛИ Инженер ИЛИ координатор). Смешанные
   правки — источник регрессий, которые не отдиагностировать.
3. **После любой правки машины:** `npm test` перед реальным прогоном.
4. **Диагностика — по правилу четырёх уровней (§18) и по `events` (SQL)**, не по
   памяти о логах.
5. **Ревью диффа руками перед коммитом — всегда.** Claude Code правит уверенно,
   в том числе уверенно неправильно.
6. **`docs/DECISIONS.md` дописывается каждой фазой:** что решено в неочевидном
   месте, почему именно так, что осознанно НЕ сделано. Это самый ценный
   документ проекта — он не восстанавливается по ТЗ.
