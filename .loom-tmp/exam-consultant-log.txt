# 1. Задача

Сделать веб-сервис, который превращает горизонтальное видео в вертикальное (9:16): пользователь либо вручную ведёт рамку мышью прямо во время просмотра, либо включает автоматику — рамка сама едет к говорящему; ручные проезды перезаписывают автоматику на своих участках. Итог — вертикальный mp4 со звуком, покадрово повторяющий превью, скачиваемый одним нажатием.

# 2. Решения

Выбран вариант A: браузерный canvas-превью (для мгновенного отклика мыши и переигрывания) + сборка финального файла одним проходом ffmpeg через crop-команды из той же дорожки выборок 30 Гц, что рисует превью — так гарантируется покадровое совпадение. Определение говорящего (лица + рассинхрон губ/звук) тоже считается в браузере, а не на сервере, чтобы автоматика была видна сразу при воспроизведении, а не после round-trip'а. Отброшены: полностью клиентский рендер (B) — противоречит §6 ТЗ и хрупкий мукс mp4 в браузере; покадровый PNG-конвейер (C) — слишком медленный; серверный ML-анализ говорящего (D) — теряет свойство «видно сразу». Ключевое решение ТЗ («одна дорожка, ручной проезд перезаписывает отрезки») реализовано как единый массив выборок с флагом источника (auto/manual) на каждой точке.

# 3. Что сделано

Из 12 задач в дереве: **done — 6**, **blocked_needs_human — 2**, **pending — 4**.

Готово и покрывает признаки:
- Каркас: сборка, express-сервер, страница с плеером
- Ядро: единая дорожка положений рамки (авто-слой + ручные перезаписи + клэмп по границам кадра)
- Ядро: выбор говорящего и построение авто-дорожки (в изоляции, не в UI)
- Плеер: загрузка файла, вертикальная рамка во весь кадр, превью справа
- Ручное ведение мышью: следование, упор в края, запись и повтор
- Сервер: сборка вертикального mp4 по треку с индикатором прогресса

Тестовые фикстуры формально помечены done, но приёмка на них не проходит (см. §5).

# 4. Как проверено

**Контур 1 (критерии задач):** по большинству done-задач критерии подтверждены прогонами приёмки (браузерные сценарии playwright-типа: клэмп по краям, sampleTrack на записанных участках, повтор после перемотки, наличие jobId/прогресса при сборке). Точные числа "X из Y" по каждому критерию не переданы — известен только статус задачи целиком. По задаче с фикстурами критерий формально не пройден (см. ниже) при фактически рабочем результате.

**Контур 2 (Пилот):** **не запускался** — доска не была полностью зелёной на момент сдачи (два blocked_needs_human), поэтому сквозной проверки «загрузил файл → провёл рамку → включил автоматику → скачал и посмотрел файл» никто не делал. Это значит, что даже для «done»-задач нет подтверждения их совместной работы как целого продукта.

# 5. Что хромает

- **Фикстуры-генератор**: ffmpeg реально создаёт тестовые ролики (wide.mp4, wide2.mp4) без ошибок, но приёмочная проверка сравнивает stdout строго с `'FIXTURES_OK'`, а скрипт пишет туда же свои логи через `stdio:'inherit'` — критерий математически недостижим в текущей формулировке. Функциональность есть, тест сломан.
- **Автоматика в браузере (#auto)** — заблокирована, реализации нет вообще: FaceSource, анализ звука, заполнение авто-слоя, приоритет ручного проезда над авто — ни один шаг не подтверждён. Это закрывает признак 6 (переключение авто/ручное на соседних участках) и фактически всю "автоматическую" половину продукта.
- **Точность экспорта (#api/render)** — сервер отвечает `invalid_track` на валидный по смыслу трек ещё до старта рендера; ни один экспортированный файл не был получен и не сравнивался с превью. Признак 8 (покадровое совпадение экспорта) не проверен ни разу фактически, хотя сборка mp4 с прогрессом (другая задача) формально done — неясно, действительно ли скачанный файл соответствует превью.
- Обе blocked-задачи упёрлись не в сложность реализации, а в недоступность шлюза модели (таймаут провайдера claude-cli:opus) — это инфраструктурная причина, не архитектурная.
- Сборка нового файла, сброс состояния, README и финальная регрессия не начаты — при текущем состоянии их всё равно нельзя было бы честно проверить, пока не работает автоматика и экспорт.

# 6. Что требует тебя

1. **Ручное ведение мышью** и **Автоматика в браузере** — обе последние попытки упёрлись в таймаут шлюза coder (claude-cli:opus), без единого прогона кода. Нужно решение: сменить провайдера/модель для роли coder, увеличить timeout+ретраи, либо прогнать code_hint вручную — сам код для автоматики не написан.
2. **Точность экспорта** — открытый вопрос по контракту: что источник истины для длительности трека — клиентский `track.duration` или серверный ffprobe исходника. Предложен вариант: сервер берёт длительность из ffprobe, а не из присланного трека, и валидирует только структуру samples. Нужно подтвердить это решение — без него рендер вообще не стартует.
3. **Формат вывода фикстур** — выбрать: либо переносить логи скрипта в stderr (чтобы stdout был чист под `equals 'FIXTURES_OK'`), либо ослабить критерий до `contains`. Разница на 5 минут работы, но без решения задача формально не закрывается.
4. Из-за первых двух пунктов Пилот вообще не запускался — сквозной проверки продукта нет. Решение о приоритете (чинить шлюз vs руками применять code_hint) определяет, когда появится первый честный e2e-факт.

# 7. Следующий шаг

Сначала снять инфраструктурный блокер шлюза (или обойти его через ручное применение готовых code_hint — они уже сформулированы и локализованы), чтобы получить хотя бы один живой прогон автоматики и экспорта. Затем поправить контракт /api/render (источник истины — ffprobe) и формат вывода фикстур — это быстрые правки. После этого прогнать весь конвейер вручную (загрузка → ручное ведение → автоматика → ручная перезапись поверх → скачивание) и только тогда запускать Пилота на контур 2, чтобы получить первую реальную оценку покадрового совпадения экспорта с превью — это сейчас главный неизмеренный риск продукта.
